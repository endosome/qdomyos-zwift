# W1 control validation, 2026-10-14

Windows Bluetooth through WSL can now control this W1 locally. Native Linux
Qt/BlueZ diagnostics remain available. The controller uses QZ's restricted
FitShow queue and packet encoder, with a native Windows identity/limit/command
gate and independent stale-status/input-loss watchdog. No initialization replay
was needed in the successful sessions.

## Confirmed controls

| Control | Captured protocol evidence | Operator evidence |
|---|---|---|
| Start | 53/01 reply, countdown 3/2/1, RUNNING | Belt started without physical controls |
| Speed | Raw targets 10, 12, 15, 20, 30, 40, 50, 60 and return to 10 | Display 1.0–6.0 and expected physical changes |
| Incline | Codes 0 → each of 1–8 → 0 at raw speed 10 | Expected deck movement and return |
| Stop | 53/03 reply, deceleration reports, then NORMAL | Physical stopping confirmed |

There are sixteen physically confirmed named start/speed/incline trials. Speed
and incline messages are paired targets; no percent-grade mapping is implied.
Live walking bounds were consistently 10–60/tag 0 and incline 0–8 during these
motor trials. Module identity was freshly checked as FITSHOW/FS-BT-C1/software
1.3.8; firmware remains unknown. Notification cleanup succeeded.

## Findings that changed the implementation

- Five seconds of stop observation was too short for the speed-40 trace: the
  observer ended after two NORMAL samples despite operator-confirmed stopping.
  The window is now ten seconds; a delayed-stop regression passes.
- RUNNING reported raw 10 after the return target, but a subsequent STOP trace
  began at raw 17. Status speed may differ by state or represent a setpoint;
  independent attained belt-speed semantics remain unresolved.
- Pause 53/06 received no reply. Initially the pending-ACK queue suppressed
  status polling, and Windows' stale-status watchdog delivered the fallback
  stop. The operator saw the expected eventual stop, but this did not prove pause.
- The restricted queue now polls status while awaiting a reply without retrying
  the pending motor command or extending its deadline. All 47 Core checks pass.
- A focused live pause repeat with that fix returned RUNNING/raw 10 at three
  polls after pause. No pause reply arrived. The existing two-second command
  deadline then triggered explicit stop; stop/reply/deceleration/NORMAL and
  cleanup succeeded. Pause/resume stays unsupported on this verified path.
- SAFETY 0x06 and unavailable identity caused preflight refusals without motor
  writes. Wake/connection behavior remains inconsistent; guards were retained.

## Idle polling outcome

The operator reported the display off when checked, and the experiment was ended via Q. The moment the display went dark was not observed.
The capture contains 625 NORMAL and 101 disabled 06/02 replies. First NORMAL:
15:35:57.412 UTC; first 06/02: 15:41:40.711 UTC, 343.3 seconds later. Status

maximum write gap 562 ms. Both capability queries were sent once. No motor

This disproves status polling as a display keepalive for this setup. The 343.3s
interval is from the first observed NORMAL, not the last physical interaction;
it does not establish the exact firmware idle timeout.

The official FitShow treadmill protocol was retrieved from its publisher and
is archived under `references/fitshow-treadmill-protocol-v1.1-2017.pdf`. It
confirms disabled detail 2 is sleep and documents READY mode with compatibility
bit 0x80 as a candidate for further investigation. It also makes clear that
53/01 with the high bit clear starts the treadmill. Treat READY as motor-capable,
not as a harmless keepalive query. No such trial or fixed keepawake policy has
been implemented or validated yet.
